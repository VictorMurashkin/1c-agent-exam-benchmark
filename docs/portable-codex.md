# Codex на Windows, Linux и macOS

Портируемый путь исполнения предназначен для **Codex CLI**: `harness=none` либо
установленный нативный харнес с принятой локальной квитанцией проверки
([подготовка харнесов](harnesses.md)). Создание планов не запускает Claude.
Исторический адаптер и результаты Claude сохранены. На Windows/Linux исполнитель
отклоняет дополнительные харнесы, отсутствующие в локальном реестре нативных установок,
до обращения к модели.

MCP-серверы выбранного харнеса передаются Codex с `required=true` через аргументы
`-c`, в том числе при `--ignore-user-config`. Codex ожидает их инициализации в пределах
настроенного `startup_timeout_sec`; если сервер не стартовал, запуск завершается ошибкой.
Без этого требования необязательный сервер может не попасть в начальный каталог
инструментов: текущий CLI по умолчанию ждёт такие серверы лишь 1000 мс независимо от
более длинного таймаута запуска
([параметры MCP в Codex](https://learn.chatgpt.com/docs/extend/mcp)).
Отдельная проверка пакета без модели подтверждает
работу сервера, но доступность инструментов агенту проверяется живым MCP-вызовом
через выбранную версию Codex.

## Установка и проверка без модели

Нужны Git, Python 3.11+ и Codex CLI. Для экзамена дополнительно нужна лицензированная
1С для выбранной ОС и исходный каркас `.dt`; они не скачиваются через pip.

Windows PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e .
.\.venv\Scripts\python.exe -X utf8 -m exam_bench.cli doctor
.\.venv\Scripts\python.exe -X utf8 -m exam_bench.cli selftest
.\.venv\Scripts\python.exe -X utf8 -m unittest discover -s tests
.\.venv\Scripts\python.exe -X utf8 -m exam_bench.cli site --catalogue-only
```

Linux/macOS:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -e .
.venv/bin/python -X utf8 -m exam_bench.cli doctor
.venv/bin/python -X utf8 -m exam_bench.cli selftest
.venv/bin/python -X utf8 -m unittest discover -s tests
.venv/bin/python -X utf8 -m exam_bench.cli site --catalogue-only
```

Каталог задач открывается на `http://127.0.0.1:8879/`. Режим `--catalogue-only` не
требует исторических кампаний и не показывает их результаты. Обычная сборка результатов
остаётся строгой: отсутствие указанного доказательства вызывает ошибку, а не пропуск.
Сервер отдаёт только `site/dist/`, а не репозиторий и `.local/`.

`doctor` показывает пути и наличие файла авторизации, но не читает/печатает токены и
не проверяет лицензию 1С или доступность модели. `selftest` проверяет захват stdout/stderr,
передачу stdin и остановку дочерних процессов по таймауту; запросов к модели нет.

## Настройки машины и границы изоляции

Стандартный экзаменационный промпт предписывает агенту добавлять
`/DisableStartupDialogs /DisableStartupMessages` при пакетных запусках
конфигуратора (`DESIGNER`) в Windows и не добавлять `/Visible`. На 1С 8.3.27.2342
загрузка XML с обновлением конфигурации БД без `/DisableStartupDialogs` показывает
окно конфигуратора даже при `Start-Process -WindowStyle Hidden`; с этим параметром
та же операция выполняется без видимых окон. `/DisableStartupMessages` сам по себе
окно не скрывает. Это требование к командам агента, а не принудительное скрытие
произвольных процессов. Оно действует на новые попытки со стандартным промптом;
уже работающий агент и явно заданные промпты проверок не изменяются.
Режим `ENTERPRISE` и сторонние MCP-серверы требуют отдельной проверки запуска.

Скопируйте подходящий `profiles/machine.<os>.example.json` в `.local/machine.json`,
исправьте путь к установленной платформе и её версию. В Windows пример содержит
`isolation=required`: это намеренный запрет запуска до явного выбора границы изоляции.
Можно выбрать другой конфиг через переменную `EXAM_BENCH_CONFIG`.

| Режим | ОС | Поведение |
|---|---|---|
| `macos` | macOS | Существующий `sandbox-exec`, реальная проверка запретов перед запуском Codex |
| `bubblewrap` | Linux | Требуются `bwrap` и разрешённые user namespaces; отдельные mount/PID/IPC namespaces, проверка запретов перед Codex; у грейдера также отдельная сеть |
| `dedicated-host` | все три | Запуск под текущим пользователем без внешней файловой/сетевой песочницы; только для отдельного тестового аккаунта/VM |
| `required` | все три | Отказ до запуска агента; автоматического перехода к полному доступу нет |

**Windows:** Job Object ограничивает время жизни дерева процессов, но не доступ к
файлам и сети. Для исполнения на выделенной Windows-машине/VM нужно явно записать
`"isolation": "dedicated-host"`. Не включайте этот режим на рабочем аккаунте с
секретами. В результатах такого запуска фиксируются `isolation_verified=false`,
`comparison_eligible=false` и ограничение методики. Это локальная техническая проверка,
а не равноценная защищённая серия macOS. Нативная файловая песочница Windows в этом
изменении не реализована. Codex получает полный доступ внутри выбранной внешней границы.

Linux по умолчанию использует Bubblewrap, если `bwrap` найден. Если namespaces запрещены
политикой ОС, проверка завершается ошибкой; песочница не отключается. Контролируемые
каталоги 1С монтируются отдельно; может потребоваться настройка `platform_cache` и
среды графической сессии для конкретного дистрибутива/лицензии. Реальный запуск 1С
на каждой машине подтверждается отдельно, он не доказан модульными тестами.

`platform_binary`, `platform_version`, `platform_cache`, `isolation` — полный список
ключей конфига. Токены там хранить нельзя. Окружение дочернего процесса формируется
по разрешённому списку; произвольные API-ключи и переменные оператора не наследуются.
Файл авторизации Codex временно копируется в отдельный `CODEX_HOME` и удаляется
после завершения/таймаута. Как и раньше, решатель может прочитать собственную копию
авторизации во время работы; для кампаний нужен отдельный аккаунт стенда.

## Проверка установленного Codex

После выбора режима изоляции и `codex login`:

```sh
python -X utf8 -m exam_bench.cli probe --model EXACT_MODEL_ID --run-id codex-native-probe-001
```

Замените `EXACT_MODEL_ID` точным доступным ID модели (`gpt-...`). Это уже реальный
запрос к модели по подписке, максимум 60 секунд по умолчанию. Он не решает экзамен
и не требует 1С. Можно передать `--client` с абсолютным путём к Codex, `--auth-seed`
с путём к его `auth.json` и `--timeout` от 1 до 300 секунд. Повторное использование
каталога прогона запрещено. Успех требует `out/probe.txt` с точными байтами `READY`.
Такая проба подтверждает клиент/модель, но не управление платформой.

## Подготовка настоящего экзамена

1. Установите 1С с лицензией; перенесите каркас `.dt` из архива старой машины.
2. Проверьте `doctor`, настройте `platform_binary` и изоляцию.
3. Выполните `prepare --binary ... --starter ... --evidence .local/environment-verified-v1`.
4. Выполните `calibrate --binary ... --starter-source .local/environment-verified-v1/src-2 --starter-dt ... --evidence .local/calibration/accepted-portable-v1`.
5. Выполните короткую `probe` с нужной моделью, сохранив успешную квитанцию.
6. Создайте новый план через `tools/create_run_plan.py --help`; укажите новую
   калибровку, каркас, путь к Codex, `--harness none` или ID подготовленного нативного
   харнеса, модель, серию и ссылку на пробу.
7. Запускайте через `exam-bench start --help`. После подготовки решателя начнётся
   отсчёт времени; проверка решения выполняется отдельно.

У всех команд выше общий префикс `python -X utf8 -m exam_bench.cli`, кроме создания
плана. На macOS сохраняется дополнительная проверка работы 1С внутри sandbox,
её выполняет перенос стенда ([new-machine.md](new-machine.md)). На новой Windows/Linux-машине паспорт,
калибровка и план должны иметь одинаковый снимок настроек машины. Для нового кода
проверяющего нужна новая калибровка; исторические квитанции автоматически не принимаются.

## Проверки переноса

Windows: проверены управление процессами, блокировка между процессами, CLI,
статические проверки, контроль хешей и сборка каталога сайта. Проверка полной
аттестации требует реальной 1С и исходных материалов. Тесты, требующие архивных
кампаний, пакетов харнесов или macOS sandbox, явно пропускаются при их отсутствии.

В `.github/workflows/portable.yml` добавлена матрица Windows/Linux/macOS × Python
3.11/3.12. Наличие workflow не означает, что удалённые проверки уже выполнены.
Из этой Windows-сессии Linux/macOS не запускались.

`.gitattributes` запрещает преобразование LF/CRLF: манифесты проверяют исходные
байты. Пути внутри манифестов и идентификаторов дефектов всегда используют `/`,
пути к исполняемым файлам и базам остаются нативными для ОС.
